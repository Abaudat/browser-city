# Story 1.4: Spike - Backup, Export and a Tested Restore

A backup path actually restored from, not a plan to build one. Everything
below is machine-checked: `scripts/ci/check-backup-restore.sh` runs the
export -> restore -> verify round trip below against a real local
SpacetimeDB instance on every server-affecting change; the numbers in
"Performance" were measured on this run's dev box
(`scripts/ops/export-world.sh`/`restore-world.sh`, timed by hand, not a
harness -- unlike 1.3's spike, this story's work is the tooling itself,
not a statistical measurement).

## AC1: Maincloud's own backup semantics

Retrieved 2026-09-11, against `spacetime --version` 2.9.0.

- **No user-facing backup, export or restore command exists in the CLI.**
  `spacetime --help`'s full command list (`publish`, `delete`, `logs`,
  `call`, `describe`, `dev`, `sql`, `mcp`, `rename`, `generate`, `list`,
  `login`, `logout`, `init`, `build`, `server`, `subscribe`, `start`,
  `lock`, `unlock`, `version`) has none. This is the premise the whole
  rest of this story is built on, confirmed directly rather than assumed.
- **Maincloud performs backups; the docs say so and nothing more.**
  https://spacetimedb.com/docs/how-to/deploy/maincloud/ (retrieved
  2026-09-11): "It handles infrastructure, scaling, replication, and
  backups so you can focus on building your application." No mention of
  frequency, retention, or a restore procedure anywhere on that page.
- **Point-in-time retention, by plan** (https://spacetimedb.com/pricing,
  retrieved 2026-09-11): Free -- not included. Pro -- 7 days. Team -- 30
  days. Enterprise -- "custom" (unquantified). Frequency within that
  window is **unknown** -- not stated anywhere found.
- **Self-serve trigger or restore without vendor support: unknown.**
  No dashboard restore control, API endpoint, or CLI command was found in
  the docs or the CLI's own `--help` output. Not inferred as "vendor
  support only" -- simply not found, which is itself the finding AC1
  asks for.
- **Billing for `spacetime sql`:** Maincloud bills compute in an
  energy unit (TeV), not per-query; the pricing calculator's line items
  are "Reducer Calls", "Egress Bandwidth" and "Table Storage" (Pro: 100,000
  TeV free credit/month). Whether a `spacetime sql` read is metered
  under one of those or separately is **unknown** -- not itemised on the
  pricing page.

**Conclusion:** the vendor's backup semantics are exactly as opaque as
this story's premise assumed. Nothing below depends on them.

## AC2/AC3: the logical export and restore

### The central platform finding: SQL cannot write everywhere it can read

`spacetime sql`'s `INSERT`/`UPDATE` grammar has no literal syntax for a
`Product` or `Sum` type
(https://spacetimedb.com/docs/reference/sql/, retrieved 2026-09-11:
"Spacetime SQL however does not support all of SATS, specifically in the
way of product and sum types... rows containing them can be returned to
clients" but not written). Confirmed empirically against a real local
2.9.0 instance, every syntax tried:

- **`Timestamp`/`ScheduleAt` cannot be written via SQL at all, in any
  form.** Every literal shape tried (`1000`, `(1000)`, `1000i64`,
  `Timestamp(1000)`, a quoted ISO string, a field-named tuple) was
  rejected. `UPDATE t SET written_at = written_at` (a no-op assignment to
  itself) was *also* rejected ("Unsupported column/variable assignment
  expression") -- a Timestamp column is read-only from SQL, full stop, not
  merely hard to construct.
- **`Identity`/`ConnectionId` are the one exception**, special-cased by
  the SQL parser as a bare `0x...` hex literal -- confirmed working for
  `module_owner.owner` and a synthetic `character_identity.identity`.
- **A second, sharper trap on that same exception:** `spacetime sql
  --format json` trims leading zero *nibbles* when it renders an Identity
  back (`900004` decimal renders as `0xdbba4`, 5 hex digits -- not the
  full 64). That shorter form is then **rejected** as an INSERT literal
  ("cannot be parsed as type U256") -- the CLI's own read output is not
  always valid as its own write input. `scripts/ops/python/canon.py`'s
  `sql_literal` left-pads back to 64 hex digits before every restore
  insert to work around this.

**Consequence for restore:** any table with a `Timestamp` or `ScheduleAt`
column cannot be restored via `spacetime sql`, at all, if it has any rows
-- not "loses precision", *cannot receive a single row*. In this schema
today that is `building`, `character`, `citizen`, `citizen_state`,
`demo_ping` and `room` (6 of 17 non-scheduled tables), plus every
scheduled table's `scheduled_at`. `restore-world.sh` refuses outright
rather than silently dropping such a table (see "Restore rules" below);
`scripts/ci/check-backup-restore.sh` asserts this refusal directly, by
seeding `demo_ping` via its one real reducer (`send_ping`) and proving the
restore stops and names the table. Today none of the other five have a
reducer that can write to them at all yet, so the gap is currently latent,
not blocking -- but the first story that adds one (a citizen-spawning
reducer, a building generator) inherits an un-restorable table unless
this finding is revisited then.

### The second platform finding: `auto_inc` does not observe an explicit-id insert

Tim's suspected trap, confirmed directly, twice: inserting an explicit id
(`object_id = 500`) via SQL and then requesting the placeholder (`0`,
the auto-generate sentinel) for a fresh row returns **1**, not 501 --
republishing the module in between makes no difference. Restored against
a table already holding higher explicit ids, the very next auto-generated
insert **collided outright** on the primary key (`IndexError: Unique
constraint violation`), not merely "not greater than the max".

**No fix exists in the tooling available to this story.** SpacetimeDB 2.9
has no `ALTER SEQUENCE`/`SETVAL`-equivalent in SQL, and no reducer-level
API to advance a table's auto_inc counter -- the only way to advance it
at all is to request the placeholder repeatedly until the counter passes
the target, which is O(max restored id) `spacetime sql` round trips: cheap
for the hundreds of ids this spike's own check seeds, completely
impractical once ids reach the thousands a real world would have. This is
recorded here as an **open platform gap**, not resolved: a restored
auto_inc table is not safe for continued play until its counter naturally
climbs past the restored maximum on its own. `scripts/ci/check-backup-restore.sh`
asserts the actual outcome (collision or advance) every run, deterministically,
rather than assuming which one occurs -- so a future SpacetimeDB
version that starts tracking this is *noticed*, not silently relied upon.

### The scripts (`scripts/ops/`)

- **`export-world.sh <db> <out-dir> [--server ...]`** -- table list from
  `spacetime describe --json`'s own `Tables` section, cross-checked
  against `server/schema.snapshot.json` (missing/extra tables abort the
  export). One `spacetime sql --format json "SELECT * FROM <t>"` per
  table; column names/order cross-checked against the snapshot too
  (name-normalised: SpacetimeDB echoes `x0` back as `x_0`, a letter/digit
  boundary rule confirmed empirically, not documented). Writes
  `<table>.jsonl` (one canonical row per line, sorted by primary key) and
  `manifest.json` (CLI version, the snapshot's own sha256, database/
  exporting identity, per-table row counts and sha256). Builds in
  `<out-dir>.partial`, renames only on full success -- a failed or
  half-written export never looks like one at the final path.
- **`restore-world.sh <db> <export-dir> [--server ...]`** -- refuses a
  schema-sha256 mismatch; refuses a target holding any row beyond
  `init`'s own seed (`module_owner`, the code tables, which restore then
  *replaces* rather than requiring empty); refuses a restoring identity
  that is not the exported `module_owner.owner` (read back from the
  target's own freshly-`init`-seeded row, since every table in this
  schema is private and SpacetimeDB itself refuses a non-owner's SQL read
  of one -- confirmed empirically to fail *before* this script's own
  identity check even runs); never restores a scheduled table (derived
  state); refuses -- does not silently skip -- a populated table it
  cannot write via SQL. Batches inserts (default 200 rows/statement,
  `BC_RESTORE_BATCH_SIZE`) and batches the *rendering* too (one `python3`
  process per batch, not per row -- an early version of this script spent
  minutes rendering 20,000 rows one process each on this dev box; one
  process per few-hundred-row batch does not).
- **`verify-world.sh <export-dir-a> <export-dir-b>`** -- compares every
  non-scheduled table's `.jsonl` file byte for byte between two exports.
  Deliberately not the only oracle: `scripts/ci/check-backup-restore.sh`
  adds `COUNT(*)` queried directly against both live databases and
  literal sentinel-value assertions read back from the restored database
  itself, independent of the export files (an exporter that drops a
  column the same way on both sides would still pass a byte-for-byte
  compare alone).
- **`seed-edge-rows.sh <db>`** -- schema-driven, from
  `server/schema.snapshot.json`'s own column list and types (never a
  hand-written per-table row): cycles every SQL-writable non-scheduled
  table's columns through integer extremes (`u8`/`u32`/`u64`
  min/max/high-bit, `i32`/`i8` min/max), an adversarial string (`'`,
  `"`, a real tab, a real newline, an emoji, the empty string), and a
  synthetic `Identity` for a `#[unique]` column. A column type with no
  entry in `canon.py`'s `EDGE_VALUES` fails loudly rather than seeding
  nothing.

### Numeric precision (why none of this uses `jq`)

`chunk_key` and every auto_inc id are `u64`; `spacetime sql --format
json` emits them as bare JSON numbers, not strings. `jq` re-serialises
every number through an IEEE double -- confirmed empirically that a
`u64::MAX` `chunk_key` (`18446744073709551615`) survives a raw
`--format json` response byte for byte but does not survive a `jq .`
pass. Python's `json` module decodes an integer literal with no `.`/`e`
to an arbitrary-precision `int` and re-emits it identically -- verified
the same way, and used everywhere in `scripts/ops/python/canon.py`
instead. This is a deliberate deviation from Tim's assumption that `jq`
alone would suffice; `python3` is already present on `ubuntu-latest` and
on this dev box, so no new tool is added, only a different one for this
specific job.

### Consistency

Each table's export is one `spacetime sql` call, its own transaction --
consistent per table, not across tables (Tim's direction, unchanged).
Acceptable for this story: nothing yet writes across two tables in the
same reducer transaction that this export would observe mid-flight.
Verification runs against the export files, not the live databases
directly, so the row-for-row claim still holds regardless.

## AC4: the restore, actually performed

**Local, every run, in CI:** `scripts/ci/check-backup-restore.sh`, wired
into `ci.yml`'s `migrate` job (already starts a local instance; no second
one). Publishes a real module, seeds every SQL-writable table with
adversarial values via `seed-edge-rows.sh`, exports, restores into a
second fresh database, exports again, and asserts byte-for-byte equality,
`COUNT(*)` equality against both live databases, literal sentinel values,
the `module_owner`/`require_owner` invariants (reusing
`check-live-migration.sh`'s own proven pattern), and three refusal paths
(non-fresh target, schema mismatch, wrong identity) plus the
Timestamp-limitation refusal above -- eleven distinct assertions, all
green as of this PR's own run.

**Maincloud:** `.github/workflows/backup.yml`'s `rehearsal` job runs the
identical scripts against two scratch Maincloud databases
(`browser-city-rehearsal-{src,dst}-<run_id>`), deleting both in an
`always()` step. **Deferred** (`docs/trace-matrix.md`): no Maincloud
credential or target-database variable exists in this repo yet
(`secrets.SPACETIME_MAINCLOUD_TOKEN`, `secrets.BACKUP_PASSPHRASE`,
`vars.BACKUP_DATABASE`) -- the workflow is real and correct by
inspection, but has not been run, because nothing yet grants CI access to
Maincloud. The blocker is naming a credential, not writing more code.

## Unattended export and its own failure reporting (AC2)

`.github/workflows/backup.yml`: daily `schedule` (an off-minute) plus
`workflow_dispatch`. A missing secret or variable is a **failure**, not a
skip (checked as its own first step). The export is `gpg --symmetric
--cipher-algo AES256` encrypted before `upload-artifact` (`retention-days:
90`) -- the repo is public, so anyone logged in can download an Actions
artifact, and a plaintext export must never be one. The passphrase itself
lives outside GitHub too (assumption: a password manager entry the
developer who sets up the secret also keeps -- without it, every backup
is unrecoverable, since only the encrypted blob is retained). Scheduled
failure (never on `workflow_dispatch`, where the failing run is its own
signal) files or updates one tracking issue via
`scripts/ci/report-scheduled-failure.sh`, extracted from
`windows-install-check.yml` so both workflows share one copy. A staleness
check (`gh run list --workflow backup.yml --status success`) fails the
run if the last successful export is more than 36 hours old, so a
schedule GitHub silently disabled (60 days with no commits, on a public
repo) or an expired secret does not go undetected between alerts.

## Performance

Measured on this dev box (Windows 11, local `spacetime start`, not
Maincloud, not a GitHub Actions runner), `placed_object` (the largest
`TABLE_BOUNDS` ceiling in the schema today, 3,000,000 rows), seeded to
20,000 rows in 20 batched `INSERT`s of 1,000 (0.9s to seed):

| Operation | Rows | Wall time | Throughput |
| --- | --- | --- | --- |
| `export-world.sh` | 20,000 (24 tables, 20,019 total) | 7.4s | ~2,700 rows/s |
| `restore-world.sh` (batch 200) | 20,000 | 20.2s | ~1,000 rows/s |
| `verify-world.sh` | 20,000 | <1s | -- |

Export file size: 673KB for 20,000 `placed_object` rows (~34 bytes/row).

**A batch size of 1,000 (5x the default) failed outright** on this dev
box -- not a SpacetimeDB error, no error message was even returned; the
process failed before the server could respond, consistent with the
Windows command-line length limit (`spacetime sql`'s query is one argv
element, and a 1,000-tuple statement is tens of kilobytes). 200 was
chosen as the default specifically because it round-tripped 20,000 rows
without incident; a Linux CI runner's much larger `ARG_MAX` may tolerate
a larger batch, untested here.

**Extrapolated to `placed_object`'s 3,000,000-row ceiling** (linear, not
re-measured at that scale -- restore's 20-second/20,000-row run is the
only real number this story has past the CI check's own small seed):
~150x this table -> **export ~19 minutes, restore ~50 minutes, ~100MB**.
That is well past what a PR-time check should ever run (Tim's <2-minute
budget), which is exactly why the scale leg is not in `ci.yml` -- it
belongs in `backup.yml`'s `rehearsal`/`schedule` path, never a PR.
50 minutes for a full-ceiling restore is also, on its own, a real
operational number worth recording rather than assuming acceptable: the
deploy story that wires a pre-migration backup (`docs/trace-matrix.md`'s
`deferred` row) inherits this as its own budget question, not an
already-solved one.

## Findings summary

1. No user-facing Maincloud backup/restore/export exists; retention is
   7/30 days (Pro/Team) point-in-time, frequency and self-serve restore
   are undocumented (AC1).
2. `spacetime sql` cannot write a `Timestamp` or `ScheduleAt` value at
   all -- a real, load-bearing platform limitation, not a tooling gap.
   6 of today's 17 non-scheduled tables are unrestorable via SQL the
   moment they hold a row; `restore-world.sh` refuses rather than drops.
3. `auto_inc` sequences do not observe an explicit-id insert and can
   collide outright on the very next auto-generated row after a restore.
   No SQL or reducer-level fix exists in 2.9. Open gap, asserted every
   run, not resolved.
4. `jq` silently corrupts a `u64` above 2^53; this story uses `python3`'s
   exact-integer JSON handling instead, confirmed byte-exact including at
   `u64::MAX`.
5. The full round trip -- including every integer extreme, an
   adversarial string, and an Identity -- is byte-exact end to end, for
   every table SQL can write to, proven every CI run
   (`scripts/ci/check-backup-restore.sh`).
6. Restore throughput (~1,000 rows/s, batch 200) does not comfortably
   reach a full-size world in CI-check time; it is a `backup.yml`-scale
   concern, not a PR-time one, and a real budget question for the
   pre-migration-backup deploy story.

**NFR39 split** (`docs/trace-matrix.md`): "the restore has been tested"
is `covered`. "Backed up before every migration" is `deferred` -- no
Maincloud deploy workflow exists yet to run `export-world.sh` before a
publish.
