# Story 1.4: Spike - Backup, Export and a Tested Restore

A backup path actually restored from, not a plan to build one. Everything
below is machine-checked: `scripts/ci/check-backup-restore.sh` runs the
export -> restore -> verify round trip below against a real local
SpacetimeDB instance on every server-affecting change; the numbers in
"Performance" were measured with `scripts/dev/run-backup-perf.sh`, a
re-runnable harness (1.3's own precedent), on this run's dev box.

**Cycle 2 correction.** Cycle 1 shipped a restore that wrote through
`spacetime sql` and documented, rather than fixed, two platform gaps it
found: SQL cannot write a `Timestamp`, and a restored `auto_inc` table's
sequence can collide with the very first row a player action inserts
afterward. Both leads' review was right that this is not "done": a
restore that cannot restore `character`, `citizen`, `building` or `room`
-- the players and the citizens -- and that leaves a live world one
insert away from a primary-key panic is not a tested backup, it is an
untested one with extra steps. This cycle moves the write path from SQL
into the module itself (`server/src/tables/restore.rs`): one
`restore_<table>` reducer per non-scheduled table, owner-gated, which
can accept every SATS type `spacetime call` carries (Timestamp included)
and which fixes the auto_inc gap by construction rather than documenting
it. The SQL-cannot-write finding below is kept in full -- it is *why*
restore goes through the module now, not an unrelated curiosity.

## AC1: Maincloud's own backup semantics

Retrieved 2026-09-11, against `spacetime --version` 2.9.0.

- **No user-facing backup, export or restore command exists in the CLI.**
  `spacetime --help`'s full command list (`publish`, `delete`, `logs`,
  `call`, `describe`, `dev`, `sql`, `mcp`, `rename`, `generate`, `list`,
  `login`, `logout`, `init`, `build`, `server`, `subscribe`, `start`,
  `lock`, `unlock`, `version`) has none. This is the premise the whole
  rest of this story is built on, confirmed directly rather than assumed.
- **Maincloud performs backups; the docs say so and nothing more.**
  https://spacetimedb.com/docs/how-to/deploy/maincloud/ (retrieved
  2026-09-11): "It handles infrastructure, scaling, replication, and
  backups so you can focus on building your application." No mention of
  frequency, retention, or a restore procedure anywhere on that page.
- **Point-in-time retention, by plan** (https://spacetimedb.com/pricing,
  retrieved 2026-09-11): Free -- not included. Pro -- 7 days. Team -- 30
  days. Enterprise -- "custom" (unquantified). Frequency within that
  window is **unknown** -- not stated anywhere found.
- **Self-serve trigger or restore without vendor support: unknown.**
  No dashboard restore control, API endpoint, or CLI command was found in
  the docs or the CLI's own `--help` output. Not inferred as "vendor
  support only" -- simply not found, which is itself the finding AC1
  asks for.
- **Billing for `spacetime sql`:** Maincloud bills compute in an
  energy unit (TeV), not per-query; the pricing calculator's line items
  are "Reducer Calls", "Egress Bandwidth" and "Table Storage" (Pro: 100,000
  TeV free credit/month). Whether a `spacetime sql` read is metered
  under one of those or separately is **unknown** -- not itemised on the
  pricing page.

**Conclusion:** the vendor's backup semantics are exactly as opaque as
this story's premise assumed. Nothing below depends on them.

## AC2/AC3: the logical export and restore

### The central platform finding: SQL cannot write everywhere it can read

`spacetime sql`'s `INSERT`/`UPDATE` grammar has no literal syntax for a
`Product` or `Sum` type
(https://spacetimedb.com/docs/reference/sql/, retrieved 2026-09-11:
"Spacetime SQL however does not support all of SATS, specifically in the
way of product and sum types... rows containing them can be returned to
clients" but not written). Confirmed empirically against a real local
2.9.0 instance, every syntax tried:

- **`Timestamp`/`ScheduleAt` cannot be written via SQL at all, in any
  form.** Every literal shape tried (`1000`, `(1000)`, `1000i64`,
  `Timestamp(1000)`, a quoted ISO string, a field-named tuple) was
  rejected. `UPDATE t SET written_at = written_at` (a no-op assignment to
  itself) was *also* rejected ("Unsupported column/variable assignment
  expression") -- a Timestamp column is read-only from SQL, full stop, not
  merely hard to construct.
- **`Identity`/`ConnectionId` are the one exception**, special-cased by
  the SQL parser as a bare `0x...` hex literal -- confirmed working for
  `module_owner.owner` and a synthetic `character_identity.identity`.
- **A second, sharper trap on that same exception:** `spacetime sql
  --format json` trims leading zero *nibbles* when it renders an Identity
  back (`900004` decimal renders as `0xdbba4`, 5 hex digits -- not the
  full 64). That shorter form is then **rejected** as a SQL INSERT
  literal ("cannot be parsed as type U256") -- the CLI's own read output
  is not always valid as its own SQL write input. Moot for restore itself
  once the write path moved to reducers (see the third trap below,
  confirmed: a `spacetime call` Identity argument accepts any valid hex
  length) -- recorded here because it was the finding that first showed
  SQL round-tripping its own output is not something to rely on.

**Consequence: SQL alone cannot restore this schema.** Any table with a
`Timestamp` or `ScheduleAt` column cannot receive a row via
`spacetime sql`, at all -- not "loses precision", *cannot receive a
single row*. In this schema that is `building`, `character`, `citizen`,
`citizen_state`, `demo_ping` and `room` (6 of 17 non-scheduled tables),
plus every scheduled table's `scheduled_at`. A `spacetime call` to a
reducer has no such limit: `#[spacetimedb::table]` structs derive
`SpacetimeType`, so a reducer taking `Vec<Row>` accepts every SATS type
SATS-JSON can carry, Timestamp included -- confirmed directly:
`restore_demo_ping(ctx, [[1,"hello world",[1789104799725368]]])` inserts
the exact microsecond value given. This is why restore goes through
`server/src/tables/restore.rs`'s reducers, not `spacetime sql`, for
every table (see "The scripts" below for `restore-world.sh`'s own
rules).

**A second SATS-JSON trap, confirmed empirically while wiring this up:**
`spacetime call`'s one positional argument *is* the reducer's one
parameter's own JSON value -- there is no outer "args array" wrapper.
`restore_layer_code(rows: Vec<{code,name,rank}>)` takes
`[[code,name,rank],...]` directly; wrapping it one level deeper
(`[[[code,name,rank]]]`, the natural reading of "one arg containing a
Vec") is rejected ("expected u32, found a sequence") the moment the
struct's own first field is scalar. `server/tools/world_backup`'s
`call-batches` emits the unwrapped shape.

**A third trap, on Identity specifically:** `spacetime sql --format json`
trims leading zero *nibbles* when it renders an Identity back (`900004`
decimal renders as `0xdbba4`, 5 hex digits, not the full 64) -- that
shorter form is then rejected as a *SQL* INSERT literal ("cannot be
parsed as type U256"), though it does not affect the reducer path (a
`spacetime call` Identity argument accepts any valid hex length).
Recorded here because it was found chasing the SQL-restore approach
cycle 1 shipped, and remains true of `spacetime sql`'s own output.

### The second platform finding: `auto_inc` does not observe an explicit-id insert -- fixed in the module, not documented around

Tim's suspected trap, confirmed directly, twice: inserting an explicit id
(`object_id = 500`) via SQL and then requesting the placeholder (`0`,
the auto-generate sentinel) for a fresh row returns **1**, not 501 --
republishing the module in between makes no difference. Restored against
a table already holding higher explicit ids, the very next auto-generated
insert **collided outright** on the primary key (`IndexError: Unique
constraint violation`), not merely "not greater than the max".

**SpacetimeDB 2.9 has no `ALTER SEQUENCE`/`SETVAL`-equivalent, in SQL or
as a reducer API** -- there is no way to *tell* it where the sequence
should be. There is a way to *make* it get there: `restore_<table>`'s
reducers never insert an explicit id (`server/src/tables/restore.rs`).
Every row is inserted with its id field set to `0` (the same
auto-generate sentinel a real reducer uses); the generated id is checked
against the row's exported id, and if the sequence is behind, the
generated row is deleted and another `0`-insert tried, consuming exactly
the ids between the sequence's current position and the target. The
sequence therefore ends exactly where the export's did -- confirmed
directly: after restoring a table with ids up to 5, the next
auto-generated insert returned **6**, not a collision, and this is now
`scripts/ci/check-backup-restore.sh`'s **strict requirement**, not an
outcome it merely records. Because the gap-fill runs inside the same
transaction as the reducer call, doing it via `spacetime sql` round trips
(what cycle 1 considered and rejected as O(max id) network calls) never
happens -- it is O(max id) *in-WASM* inserts/deletes, no CLI or network
cost per step, and the numbers in "Performance" below show it does not
dominate restore time at the scale measured.

### The scripts (`scripts/ops/`) and the native tool (`server/tools/world_backup`)

- **`export-world.sh <db> <out-dir> [--server ...]`** -- table list from
  `spacetime describe --json`'s own `Tables` section, cross-checked
  against `server/schema.snapshot.json` (missing/extra tables abort the
  export). One `spacetime sql --format json "SELECT * FROM <t>"` per
  table; column names/order cross-checked against the snapshot too
  (name-normalised: SpacetimeDB echoes `x0` back as `x_0`, a letter/digit
  boundary rule confirmed empirically, not documented). Writes
  `<table>.jsonl` (one canonical row per line, sorted by the table's real
  primary key) and `manifest.json` (CLI version, the snapshot's own
  sha256, database/exporting identity, per-table row counts and sha256).
  Builds in `<out-dir>.partial`; the previous export, if any, is moved
  aside and only deleted once the new one is fully in place, so a failed
  rename never destroys a working export.
- **`restore-world.sh <db> <export-dir> [--server ...]`** -- refuses a
  schema-sha256 mismatch; refuses a restoring identity that is not the
  exported `module_owner.owner` (read back from the target's own row,
  since every table in this schema is private and SpacetimeDB itself
  refuses a non-owner's SQL read of one -- confirmed empirically); then
  calls `begin_restore`, every non-scheduled table's `restore_<table>`
  in byte-budgeted batches (`call-batches`, default 16,000 bytes,
  `BC_RESTORE_BATCH_BYTES` -- a **byte** budget, never a row count: a
  fixed row count breaks the moment a table's average row size crosses
  the command-line length limit, 131,072 bytes for one argv element on
  Linux, roughly 32,000 characters for the whole command line on
  Windows), and `finish_restore`. `begin_restore`/`restore_*` are the
  actual guards (never restoring over a live world, never touching a
  scheduled table) -- this script only wires the calls.
- **`verify-world.sh <export-dir-a> <export-dir-b>`** -- compares every
  non-scheduled table's `.jsonl` file byte for byte between two exports.
  Deliberately not the only oracle: `scripts/ci/check-backup-restore.sh`
  adds `COUNT(*)` queried directly against both live databases and
  literal sentinel-value assertions read back from the restored database
  itself, independent of the export files (an exporter that drops a
  column the same way on both sides would still pass a byte-for-byte
  compare alone).
- **`seed-edge-rows.sh <db>`** -- calls `begin_restore`/`restore_<table>`/
  `finish_restore` with schema-driven edge-case rows on a freshly
  published database: the same mechanism restore uses, and the only
  mechanism that can write a Timestamp at all. Covers **every**
  non-scheduled table except `module_owner` (never seeded with a
  synthetic Identity -- it would overwrite the real owner every other
  `restore_*` call in the same run checks against, locking the run out
  of its own remaining tables). Cycles every column through integer
  extremes (`u8`/`u16`/`u32`/`u64`/`i8`/`i16`/`i32`/`i64` min/max), an
  adversarial string (`'`, `"`, a real tab, a real newline, a real CR, a
  backslash, a literal two-character `\n`, an emoji, the empty string),
  a synthetic `Identity`, and a Timestamp at 0/a plausible epoch
  value/`i64::MAX` microseconds. A column type with no entry in
  `world_backup`'s `edge_values` fails loudly rather than seeding
  nothing.
- **`server/tools/world_backup`** -- the pure logic (parsing/
  canonicalising a `spacetime sql --format json` response, batching by
  byte budget, schema-driven edge-value generation), native Rust, never
  a dependency of the published module (`docs/architecture.md`'s Stack
  table). Unit-tested and property-tested (`proptest`, already sanctioned
  native tooling) under `cargo test` in the `test` job -- the pure-parts-
  below-the-integration-test split both leads asked for, just not in
  Python: cycle 1 shipped `scripts/ops/python/canon.py` on the
  assumption that `jq` could not preserve a `u64` above 2^53 and Python
  could; Tim's review found `jq` 1.7+ actually does (confirmed:
  `jq 1.8.2` here passes `18446744073709551615` through `.`/`sort`
  intact). Python is removed regardless, not because the number-safety
  premise was wrong for *some* `jq`, but because real parsing logic
  belongs in the stack this repo already owns (a native binary, modelled
  on `sched_timing_report`), reading the schema through `bounds`'s own
  `ModuleSchema`/`TableDef` types rather than re-parsing
  `schema.snapshot.json` by hand. `serde_json`'s `arbitrary_precision`
  feature is what makes the exact-integer claim true for this crate,
  confirmed the same way: `18446744073709551615` and
  `9223372036854775808` round trip byte for byte through parse and
  re-serialize (`world_backup`'s own proptest suite,
  `u64_above_js_safe_integer_round_trips_exactly`).

### Consistency

Each table's export is one `spacetime sql` call, its own transaction --
consistent per table, not across tables (Tim's direction, unchanged).
Acceptable for this story: nothing yet writes across two tables in the
same reducer transaction that this export would observe mid-flight.
Verification runs against the export files, not the live databases
directly, so the row-for-row claim still holds regardless.

## AC4: the restore, actually performed

**Local, every run, in CI:** `scripts/ci/check-backup-restore.sh`, wired
into `ci.yml`'s `migrate` job (already starts a local instance; no second
one). Publishes a real module, seeds **every** non-scheduled table but
`module_owner` with adversarial values via `seed-edge-rows.sh` (Timestamp
tables included), plus a 20KB `demo_ping` message that forces a
multi-batch restore at a 4,000-byte budget; exports, restores into a
second fresh database, exports again, and asserts: byte-for-byte
equality; `COUNT(*)` equality against both live databases; sentinel
values by column on a known row; the auto_inc sequence strictly
exceeding the restored maximum (a probe reducer call, not SQL); every
scheduled table matching a freshly published reference database, byte
for byte; the `module_owner`/`require_owner` invariants (reusing
`check-live-migration.sh`'s own proven pattern); and four refusal paths
(non-fresh target, schema mismatch, wrong identity, `restore_*` called
with no restore open) -- all green as of this PR's own run, in ~27s.

**Maincloud:** `.github/workflows/backup.yml`'s `rehearsal` job (a
`workflow_dispatch` input, never the default run) publishes two scratch
Maincloud databases, seeds and exports the source through the real
`gpg`-encrypt -> `upload-artifact` -> `download-artifact` -> decrypt
path, restores, and runs the same independent verification the local
guard does (`scripts/ops/verify-independent.sh`, shared rather than
reimplemented), deleting both databases in an `always()` step.
**Deferred** (`docs/trace-matrix.md`): no Maincloud credential or
target-database variable exists in this repo yet
(`secrets.SPACETIME_MAINCLOUD_TOKEN`, `secrets.BACKUP_PASSPHRASE`,
`vars.BACKUP_DATABASE`) -- the workflow is correct by inspection, but has
not been run, because nothing yet grants CI access to Maincloud. The
blocker is naming a credential, not writing more code.

## Unattended export and its own failure reporting (AC2)

`.github/workflows/backup.yml` is `workflow_dispatch`-only (Quentin's
direction). A daily `schedule` that fails every run until
`SPACETIME_MAINCLOUD_TOKEN` exists would open a tracking issue on day one
and gain a comment every day after, training people to ignore the one
alarm that matters -- wiring the schedule back in, plus a dead-man's
switch that does not depend on that same schedule to notice it stopped
firing, is `docs/trace-matrix.md`'s `deferred` row, naming the deploy
story. A missing secret or variable is still a **failure**, not a skip
(checked as this workflow's own first step) for the runs it does have.
The export is `gpg --symmetric --cipher-algo AES256` encrypted, passphrase
piped via `--passphrase-fd 0` (stdin, never argv or a `run:` body -- a
`${{ secrets.* }}` expansion inside a script is echoed into the runner's
own command log verbatim), before `upload-artifact` (`retention-days:
90`) -- the repo is public, so anyone logged in can download an Actions
artifact, and a plaintext export must never be one. The passphrase itself
lives outside GitHub too (assumption: a password manager entry the
developer who sets up the secret also keeps -- without it, every backup
is unrecoverable, since only the encrypted blob is retained).

**Cycle 1's staleness check is removed, not fixed.** It ran *inside* the
workflow it claimed to watch, so it could never catch the one failure
mode it named (a schedule GitHub silently disabled never runs the check
either), and it ran *before* the export, so any staleness failure would
have blocked every subsequent export from ever succeeding again. Recorded
honestly rather than replaced with an unmeasured fix: a schedule going
silently disabled is undetected today, `deferred` above.

## Performance

Measured with `scripts/dev/run-backup-perf.sh` (a re-runnable harness,
1.3's own precedent), local `spacetime start`, this dev box (Windows 11,
not Maincloud, not a GitHub Actions runner), `placed_object` (the
largest `TABLE_BOUNDS` ceiling in the schema today, 3,000,000 rows), at
two sizes to show scaling rather than assume it:

| Rows | Seed | Export | Restore | Export size | Restore throughput |
| --- | --- | --- | --- | --- | --- |
| 20,000 | 0.9s | 5.7s | 5.2s | 682KB | ~3,800 rows/s |
| 120,000 | 5.7s (cumulative) | 6.4s | 24.9s | 4.1MB | ~4,800 rows/s |

Both sizes verified byte-for-byte identical to their source, including
every seeded adversarial value. Restore throughput is 4-5x cycle 1's
SQL-based figure (~1,000 rows/s): batching by byte budget (16,000
bytes/batch by default) rather than a fixed 200-row count means far
fewer `spacetime call` round trips per row at this row size, and the
auto_inc gap-fill (previously an unmeasured, separately-costed concern)
now runs in-WASM inside the same call, not as extra network round trips.

**Extrapolated to `placed_object`'s 3,000,000-row ceiling** (near-linear
between the two measured sizes, not re-measured at full scale): ~25x the
120,000-row point -> **export ~3 minutes, restore ~10 minutes, ~100MB**.
Still well past a PR-time budget (Tim's <2 minutes), which is why the
scale leg stays out of `ci.yml` -- `scripts/dev/run-backup-perf.sh` is
for a human, or `backup.yml`'s `rehearsal` path, to run deliberately.
The deploy story that wires a pre-migration backup
(`docs/trace-matrix.md`'s `deferred` row) inherits these numbers as its
own budget question, now with two real, re-runnable measurements behind
them rather than one and a linear guess.

## Findings summary

1. No user-facing Maincloud backup/restore/export exists; retention is
   7/30 days (Pro/Team) point-in-time, frequency and self-serve restore
   are undocumented (AC1).
2. `spacetime sql` cannot write a `Timestamp` or `ScheduleAt` value at
   all -- a real, load-bearing platform limitation. This is *why* restore
   goes through the module's own `restore_<table>` reducers
   (`server/src/tables/restore.rs`), not a gap the restore ships with:
   every non-scheduled table, Timestamp-bearing ones included, restores
   correctly today.
3. `auto_inc` sequences do not observe an explicit-id SQL insert. No SQL
   or reducer-level *sequence-setting* API exists in 2.9 -- but a
   reducer's own `0`-insert-then-delete gap-fill reaches the same end
   state without one, confirmed: the sequence ends exactly where the
   export left off, asserted as a strict requirement every CI run, not
   merely observed.
4. `spacetime call`'s one positional argument is the reducer's one
   parameter's own JSON value, with no extra wrapping array -- confirmed
   empirically (an extra `[...]` level is rejected the moment a struct's
   first field is scalar).
5. `jq` silently corrupts a `u64` above 2^53 (though `jq` 1.7+ handles it
   better than cycle 1 assumed -- see the scripts section above); this
   story's parsing/canonicalisation lives in `server/tools/world_backup`
   (native Rust, `serde_json` `arbitrary_precision`) instead, confirmed
   byte-exact including at `u64::MAX` by its own proptest suite.
6. The full round trip -- every integer extreme, an adversarial string
   (quote/tab/newline/CR/backslash/emoji), an Identity, and a Timestamp
   -- is byte-exact end to end, for **every** non-scheduled table, proven
   every CI run (`scripts/ci/check-backup-restore.sh`).
7. Restore throughput is ~3,800-4,800 rows/s at the two sizes measured
   (byte-budgeted batching, not a fixed row count); a full-ceiling
   restore is a `backup.yml`-scale concern, not a PR-time one, and a real
   budget question for the pre-migration-backup deploy story.

**NFR39 split** (`docs/trace-matrix.md`): "the restore has been tested"
is `covered`. "Backed up before every migration" is `deferred` -- no
Maincloud deploy workflow exists yet to run `export-world.sh` before a
publish.
