# Story 1.14: Boot Budget Measured

A harness, not an anecdote: every number below was produced by
`scripts/dev/run-boot-budget-spike.sh`, re-runnable with one command. The
raw per-sample JSON it wrote is committed alongside this file under
`docs/spikes/1.14-boot-budget/*.json`; `scripts/dev/generate-boot-budget-
report.mjs` -- calling the same pure functions
`client/tests/e2e/boot-budget/reduce.mjs`'s vitest suite exercises --
produced every table below from that raw JSON, never a hand reduction.

**MISSED, and not close.** Every measured network/CPU profile's p75
end-to-end time is 2.6-5.6x the 1000 ms pre-registered budget. The
dominant term, on every profile, is **atlas**: fetching and decoding the
street crowd's character-generator sheets, which today means 105 separate
image requests (3.0 MB) with no atlas and no batching. D4's chunking
migration is **opened**: the 28,000-row decode's throttled-profile p95 is
4,488.6 ms against a 150 ms trigger -- roughly 30x over. Per the
pre-registered rule (Tim's/Quentin's direction), this finding is recorded
against A4 (`docs/gdd.md`) and R5/D6 (`docs/architecture.md`'s "Boot
budget" section, added by this story) below, with no tuning of the budget,
the profiles or "controllable" after the numbers were read.

## Pre-registered budget

Written before any number in this run was read, and never edited
afterwards (both leads' direction, and the same discipline story 1.3's
report sets).

**Total 1000 ms, reference machine, per-term split:**

| Term | Budget (ms) |
| --- | --- |
| bundle | 250 |
| defs | 50 |
| atlas | 250 |
| handshake | 150 |
| subscriptionDecode | 150 |
| toControllable (remaining time to player-controllable) | 150 |
| **total** | **1000** |

**D4's pre-registered revisit trigger:** the 28,000-row decode passes if
its throttled-profile p95 is <= 150 ms. Anything above that opens D4's
chunking migration -- named in exactly those words, per Tim's direction.

**Verdict statistic:** p75, against the total budget. Tim's own budget
framing calls it a median target; Quentin's direction is explicit that the
verdict itself reads p75 ("no tuning... after the numbers are read"), the
stricter of the two central tendencies -- resolved in Quentin's favour so
a bar barely met on the exact median is never called "met" here.

**Minimum sample size:** 20 cold samples per profile (Quentin's floor),
met on every profile below, milestone and decode sweep alike.

## Method

**Harness, never the dev server.** `scripts/dev/run-boot-budget-spike.sh`
starts a disposable local SpacetimeDB instance, publishes `server/`
(`browser_city`) to one database and `server/spikes/boot_budget` to a
second, builds the *production* client (`npm run build`) against the
first, serves it with `vite preview`, and runs the `boot` Playwright
project (`client/tests/e2e/boot-budget/boot-budget.spec.ts`) against that
preview server -- never the Vite dev server, which serves unbundled ESM
and would measure the wrong thing entirely.

**Cold means cold.** Every sample is a fresh `browser.newContext()`: no
HTTP cache (`Network.setCacheDisabled`), no service worker, no storage
carried over from the previous sample.

**Two network profiles, two CPU profiles**, both named constants in
`client/tests/e2e/boot-budget/profiles.mjs` (the one place they are
declared -- the spec that drives CDP with them, the report generator, and
their own vitest-tested reducer all import the same file, never a second
copy):

| Profile | Description |
| --- | --- |
| `domestic` network | 50 Mbps down / 10 Mbps up / 30 ms RTT (Tim's own fixed figure; Quentin's independent assumption for the same profile used 20 ms -- resolved in Tim's favour, network-stack specifics being his call) |
| `pessimistic` network | 10 Mbps down / 10 Mbps up / 60 ms RTT (Quentin's second profile; upload bandwidth is Crew's own assumption, symmetric with domestic) |
| `reference` CPU | no CPU throttle -- this run's own real machine (see the Environment caveat below) |
| `throttled` CPU | CDP `Emulation.setCPUThrottlingRate` 4x -- both leads' stand-in for a mid-range laptop, reproducible on any machine, CI included |

**Does CDP throttling reach WebSocket traffic?** Tim asked this be checked,
not assumed. Checked empirically before committing the harness design: two
single-sample runs against a real, published `browser_city` database on
loopback, one with `Network.emulateNetworkConditions({ latency: 0 })`, one
with `latency: 200`. The `handshake-open` mark (relative to `main-start`)
moved from 12.0 ms to 221.5 ms -- a ~210 ms increase for a 200 ms extra
RTT applied once each way. **Confirmed: CDP throttling does reach
WebSocket connection establishment** on this Chromium version, at least
against loopback. A real, non-loopback TLS+WebSocket upgrade (Maincloud
included) is not measured by this spike -- see Outstanding.

**Milestones are permanent, production code**
(`client/src/boot/boot-marks.ts`), not a spike-only hook: `main-start`
(first line of `main()`), `handshake-open` (`DbConnection`'s `onConnect`),
`subscription-applied` (the first subscription's `onApplied`),
`atlas-ready` (every texture the street scene loads before its first
frame -- the static tiles *and* the street crowd's own part sheets, moved
here in this story's own cycle after the first cut placed it too early and
silently double-counted the atlas term against `toControllable`),
`first-frame-rendered`/`interactive-prompt`/`player-controllable` (FR144's
name prompt does not exist yet, so the latter two are stand-ins, fired
together at the street scene's first rendered frame, once the keyboard
listener is already attached). `first-paint` is read from the browser's
own `first-contentful-paint` entry, never a mark.

**`player-controllable` is proven honest, not assumed.**
`client/tests/e2e/boot-marks.spec.ts` (the default `chromium` project, not
`boot`) polls for the mark, presses a movement key the instant it appears,
and asserts the real, mounted scene's player position actually changes on
a following frame -- a mark that fired early would fail this test.

**Attribution.** Each term is its own self-contained wall-clock duration
for its own phase (Resource Timing for `bundle`/`defs`/`atlas`, marks for
`handshake`/`subscriptionDecode`/`toControllable`), not a disjoint slice of
the total -- the handshake and the (today, trivial) `demo_ping`
subscription proceed concurrently with the defs/atlas fetch in the real
boot sequence, so the terms do not have to sum to the total.
`reduce.mjs`'s `summarizeTerms` computes the unattributed remainder
(`total - sum(terms)`) explicitly, per sample, rather than hiding it or
forcing a false reconciliation (Quentin's direction) -- it reads small and
positive throughout this run (150-470 ms at p75), consistent with ordinary
scheduling gaps between phases, not a broken decomposition.

**D4's decode sweep** publishes `server/spikes/boot_budget` -- a
column-for-column copy of `browser_city`'s own (already-landed, not yet
subscribed-to) `PlacedObject` table, seeded via its `seed_rows` reducer at
7,000/14,000/28,000/56,000 rows, the real `sim::world::chunk_key` packing
included. `client/tests/e2e/boot-budget/decode-harness.ts` is a standalone
page (its own generated bindings, its own Vite build,
`vite.decode.config.ts`, into `dist-boot-budget-decode/` -- never
`client/dist`) that times `subscribe()` to that subscription's own
`onApplied`, and reads bytes on the wire from CDP's own
`Network.webSocketFrameReceived` frames (Resource Timing reports 0 bytes
for WebSocket traffic on this Chromium version -- confirmed empirically,
not assumed).

Bytes on the wire scale exactly with row count (one row = ~14.9 bytes,
compact BSATN): 7,000 rows = 104.9 KiB, 14,000 = 206.3 KiB, 28,000 = 409.9
KiB, 56,000 = 816.3 KiB -- decode cost is not a bandwidth problem at any
of these sizes (even 56,000 rows is well under 1 MB), it is per-row
processing cost, roughly linear in row count (7k->56k is an 8x row
increase for a ~7-8x time increase on every profile).

**D4's pre-registered revisit trigger is opened.** The 28,000-row
decode's `domestic`/`throttled` p95 is **4,488.6 ms**, ~30x the 150 ms
trigger. Every other profile at 28,000 rows is slower still (pessimistic
reaches 6.0-6.3 s). Per the pre-registered rule, D4's chunking migration
-- subscribing to a narrower halo of chunks than "the whole street" at
first paint, rather than the full ~28k-row set -- is the candidate the
architecture doc's "Boot budget" section now names as reopened.

## Verdict

**The one-second boot is not achievable against today's boot path.**
Every profile misses the budget by 2.6x-5.6x, and the two dominant costs
are structural, not incidental: no sprite atlas (105 individual image
requests for one street's crowd, 75-84% of total boot time by itself) and
no subscription chunking (a full-street `placed_object` set, ~28k rows,
costs 3.5-4.5 s to decode even on the reproducible `domestic`/`throttled`
profile, against a 150 ms trigger). Per the pre-registered rule, this
finding is recorded against **A4** (`docs/gdd.md`) and against **D6**
(the boot design) and **R5** (the standing risk) in `docs/architecture.md`'s
new "Boot budget" section -- both reopened by this report, with no
compensating tuning of the budget, the profiles or "controllable" applied
after these numbers were read.

**What this spike does not prescribe.** Whether the fix is a real sprite
atlas, per-chunk (rather than per-street) subscription at first paint, or
both, is a design decision for whoever revisits D4/D6 next -- this report
hands that decision a measured baseline and a measured decode-cost curve,
not a fix folded into the spike itself (the same discipline story 1.3's
report set for D7).

## Outstanding

- **A real, non-loopback WebSocket upgrade** (Maincloud included) is not
  measured here -- only a local SpacetimeDB instance is. The CDP-throttling
  check above confirms the harness's own network emulation reaches
  WebSocket frames against loopback; a real TLS+WebSocket handshake to a
  server that is not on the same machine carries its own connection-setup
  cost this run cannot see.
- **The reference-machine rows are a real dev box, not a literal mid-range
  laptop.** Re-running `scripts/dev/run-boot-budget-spike.sh` on one is one
  command away, not gathered by this PR.
- **The atlas term measures today's boot path**, which streams every
  character-generator sheet the mounted street crowd references, not a
  purpose-built sprite atlas -- there is no atlas to measure yet (Tim's
  direction); this is the evidence for whether building one is worth it,
  not a measurement of one.
- **NFR1's own PR-blocking regression gate does not exist yet** -- 20 cold,
  throttled samples is too slow and too noisy for every PR (both leads'
  direction). `.github/workflows/ci.yml`'s `client-build` job gates the two
  dominant terms cheaply instead: a gzipped size budget on the production
  bundle and on the public PNG catalogue, set from this run's own numbers
  plus margin, so a regression in either fails a PR in seconds without a
  browser. The full measurement above runs on `workflow_dispatch` and on
  push to master touching `client/**`, `server/**`, `defs/**` or
  `ModernTileset/**` (`.github/workflows/boot-budget.yml`), uploading its
  raw samples as an artifact -- never gating a PR. `docs/trace-matrix.md`'s
  NFR1 row is `partial` and names the story that builds the real boot path
  (FR144-146) for the rest.
