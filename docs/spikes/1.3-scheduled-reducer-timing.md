# Story 1.3: Scheduled-Reducer Timing Fidelity

A harness, not an anecdote: every number below was emitted by
`scripts/dev/run-sched-timing-spike.sh`, re-runnable with one command. The
raw per-fire observations it exported are committed alongside this file
under `docs/spikes/1.3-scheduled-reducer-timing/*.csv`; `republish-
summary.json` alongside them carries the republish leg's before/after
pending record (never a duplicated copy of the fires themselves --
`republish-leg.csv` already has those). `sched_timing_report` -- never a
hand reduction -- produced every table below, including the observer-
lateness and republish-classification ones.

**Cycle 1 correction.** The first cut of this spike measured its two
repeating probe shapes against two different reference frames:
`ScheduleAt::Interval` against a fixed origin, and a hand-rolled chained
one-shot against its own just-updated `scheduled_at` -- a moving
goalpost that absorbs every millisecond of lateness before the next
measurement, so it could never show compounding no matter what the
platform did. Read that way, the report concluded the platform's own
repeat was the thing to distrust. It was wrong: re-anchored to a fixed
origin, the chained one-shot compounds at the same rate as
`ScheduleAt::Interval` (both leads independently recomputed this from the
committed cycle-1 CSV and found it). This run fixes the measurement (one
reference frame for every repeating mode -- see
`server/spikes/sched_timing/src/lib.rs`'s module doc comment) and adds
the probe shape the comparison was actually missing.

## Pre-registered budget

Written before this run's numbers were read, per the acceptance
criteria's own instruction not to declare "acceptable" after the fact.
Unchanged from cycle 1 -- the budget did not need correcting, the
measurement did.

**Cycle 2 addendum.** Tim's cycle-2 review found the phase-preserving
pattern (`ONESHOT_ANCHORED`) this report hands to D7 has an unmeasured
failure mode: re-anchoring to the original target with no further care
means a target still in the past dispatches immediately, so a pause
longer than one bucket (a deploy, a host stall) produces a back-to-back
catch-up burst. A fourth leg (below) measures it: real, bounded, and it
converges. `docs/architecture.md` now states the second half of the
rule this implies.

- **Per-fire dispatch budget: 2.5 real seconds.** FR1 fixes the
  compression ratio at 24 in-city minutes per real minute (60 real
  minutes = 1 in-city day = 1440 in-city minutes). A citizen whose
  scheduled arrival is off by up to one in-city minute reads as "on time"
  to a player who is not staring at a clock; one in-city minute is 2.5
  real seconds. Any single fire landing within 2.5s of its scheduled time
  is within what the design can already absorb.
- **Non-compounding requirement: no unit, a shape.** A repeating cadence
  must not accumulate lateness tick over tick. Even a per-tick increment
  far under the 2.5s budget is unacceptable if it is systematic, because
  a long-running cadence (a session-length L2 tick, the day-night cycle)
  will walk arbitrarily far from its origin given enough ticks regardless
  of how small each individual increment is.
- **If either is violated,** this report says so plainly and the finding
  is recorded against risk R10 and decision D7: the Alarm Clock decision
  is reopened. No compensating correction, catch-up term or smoothing is
  added in this PR to make the number look better (Quentin's and Tim's
  direction, both).

## Method

Three quantities, never conflated in one column (per fired `observation`
row, written by the module's own `fire_probe` reducer):

- **Dispatch drift**: `ctx.timestamp` (the reducer's own view of "now")
  minus the row's expected fire time, read entirely inside the module.
  For every *repeating* probe shape (below) the expected time is the same
  fixed-origin formula regardless of how the row reschedules itself:
  `run_start_micros + (sequence + 1) * bucket_ms`. Only `BURST` (a single
  independent fire, no chain) reads its own `ScheduleAt::Time` field
  directly. One reference frame per fired row, not two under one column
  heading.
- **Commit lateness** is the same quantity for practical purposes here:
  the module never touches a network or filesystem, so "dispatch" and
  "commit" do not diverge measurably at this workload.
- **Observer lateness**: when a subscribed client actually saw the
  resulting row, via `spacetime subscribe`, each line stamped with the
  wall-clock micros it arrived at. Local loopback, one machine, so client
  and server share a clock -- the one place in this spike a client
  wall-clock read is the right tool, because the acceptance criterion is
  phrased about what a player (on the far side of a subscription) sees.

Four probe shapes:

- `ONESHOT_CHAINED` -- `ScheduleAt::Time`; the reducer reinserts a fresh
  one-shot at `fired_at + bucket`. Reschedules from *actual fire time*,
  so lateness carries forward. Compounds by construction.
- `ONESHOT_ANCHORED` -- `ScheduleAt::Time`; the reducer reinserts at
  `<this fire's own fixed-origin target> + bucket`, never at `fired_at`.
  The candidate mitigation cycle 1's review asked for: if anything can
  hold phase indefinitely on this platform, this is the shape that
  should.
- `INTERVAL` -- `ScheduleAt::Interval`, the platform's own repeat.
- `BURST` -- `ScheduleAt::Time`, single fire, no reinsertion -- the
  load legs' batch and the republish leg's one-shots.

Plus a **per-fire-cost comparison**: one `INTERVAL` probe writes nothing
beyond its own observation row (the ladder default); one writes
`WORK_EXTRA_WRITES` (50) additional throwaway rows per fire, simulating a
heavier reducer body. If the compounding rate scales with this, it is
per-fire cost, not a platform constant (Quentin's direction).

Three legs, all fire-floor-asserted (Quentin's direction: a stalled
scheduler must fail the run, not silently render a shorter table):

1. **Idle ladder** -- all four probe shapes at 100ms/500ms/1s/10s/30s/
   60s/600s, plus the per-fire-cost pair, on an otherwise-idle instance.
2. **Under load** -- `ONESHOT_CHAINED` and `INTERVAL` at the fast end of
   the ladder (100ms/500ms/1s), repeated with a burst of 1,000 and then
   10,000 rows independently due in the same tick.
3. **Republish while pending** -- one-shots seeded across
   5s/15s/30s/60s/120s/300s/600s plus one repeating row, republished over
   (no `--delete-data`) before any of them fire, then observed.
   `sched_timing_report republish` classifies survival by cross-
   referencing the before/after pending snapshot against the leg's own
   CSV -- fired, still pending, or vanished are three different platform
   behaviours, never collapsed into one "survived" bucket.
4. **Catch-up** (cycle 2) -- one `ONESHOT_ANCHORED` probe seeded with its
   origin already `CATCHUP_BACKDATE_MS` in the past (default 10,000ms at
   a 100ms bucket, so ~100 targets are already due at seed time). No
   compensation logic anywhere for this: `seed_oneshot_anchored_backdated`
   seeds the exact same chain the idle leg does, just backdated, so
   whatever happens is the platform's behaviour. `sched_timing_report
   catchup` finds the first gap between consecutive fires at least half a
   bucket wide (real-time cadence resuming) and reports the burst fire
   count, its duration and dispatch rate up to that point.

Observer lateness is measured twice: once on the idle leg (100ms buckets
present, thousands of fires/second at points) and once on the republish
leg (~1 fire/second, no fast buckets) -- Tim's direction, to separate a
subscription-saturation artefact from an actual platform number.

**The corrected finding.** `oneshot-anchored` (reschedules from its own
fixed-origin target, never from `fired_at`) holds phase: cumulative slip
is ~0 ms/tick at every bucket (-0.32 to +2.94 ms/tick, no trend with
bucket size or run length), median drift a flat 5.8-8.8ms -- per-fire
jitter, not compounding, exactly Quentin's prediction. `oneshot-chained`
and `interval` -- the two shapes that reschedule from *actual fire time*
-- compound at the same rate as each other at every bucket, from 100ms to
600s: **+7.4 to +11.2 ms/tick**, both shapes, no exception. This is not
"the platform's repeat is broken, use a hand-rolled one instead" (cycle
1's conclusion, from a measurement bug): it is that *any* repeat
mechanism that re-anchors to when it actually ran, rather than to when it
was supposed to run, accumulates its own dispatch cost indefinitely --
`ScheduleAt::Interval` and a hand-rolled chain both re-anchor to fire
time, so both compound identically. `ScheduleAt::Time` is not
implicated; how the reinsertion target is computed is.

**Per-fire-cost comparison.** `idle-interval-1000` (no extra writes)
compounds at +9.33 ms/tick; `idle-interval-work50-1000` (50 extra
`scratch` writes per fire) compounds at +9.61 ms/tick -- a 0.28 ms/tick
difference for 50x the table writes. This is a much smaller effect than
"the rate is proportional to the reducer's own work" would predict: at
this scale, the ~9-10 ms/tick baseline reads as mostly *fixed*
per-dispatch overhead (scheduler bookkeeping, the transaction commit
itself), with only a small marginal cost per additional write, not a
rate that scales linearly with reducer body size. The direction of the
effect (heavier body -> higher rate) is right; the magnitude does not
support treating "about 250 * bucket_ms to blow the budget" as a law
that scales with L2 tick weight -- it is closer to a platform-side fixed
cost than cycle 1 assumed, though still not a documented constant (see
Verdict).

## Catch-up leg

One `ONESHOT_ANCHORED` probe seeded 10,000ms behind at a 100ms bucket
(~100 targets already due), observed for 20s. `sched_timing_report
catchup`, never by hand:

> n=303, bucket=100ms: catch-up burst fired 115 time(s) in 1529.323 ms
> (75.2 fires/s), then resumed real-time cadence. Worst overdue fire:
> 9910.982 ms late.

**The pattern this report hands to D7 has a catch-up hazard, and it is
bounded, not unbounded-in-practice.** Re-anchoring to the original
target with no further care does exactly what Tim's review predicted:
the first fire lands ~9.9s late (matching the backdate), and the
following ~114 fires dispatch back-to-back at roughly 75 fires/second --
not one-at-a-bucket -- until the anchor catches up to real time, at which
point cadence returns to normal with no further compounding. For a
100ms-bucket L2 tick, a pause of `N` buckets costs roughly `N / 75`
seconds of back-to-back dispatch immediately after the pause ends, not
forever, but not free either: a deploy pausing such a tick for a minute
would cost ~8 seconds of the busiest dispatch this spike measured,
immediately on resume. This is why `docs/architecture.md` states bounding
catch-up (skip missed ticks, or clamp the elapsed-time delta simulated)
as part of the phase-preserving pattern, not an optional refinement of
it.

## Observer lateness

Measured twice, `sched_timing_report observer` on both raw logs (never
reduced by hand):

- **Idle leg** (100ms buckets present, thousands of fires/second at
  points): n=1,734, median 22,934ms, p95 62,543ms, max 66,796ms.
- **Republish leg** (~1 fire/second, no fast buckets): n=651, median
  35.2ms, p95 192.8ms, max 521.7ms.

The idle leg's own `spacetime subscribe` process only ever received
1,734 of the leg's ~72,000 fires -- it is not sampling dispatch latency,
it is a subscription stream that fell behind and stayed behind for the
whole 31-minute run, so every number in that bullet is a **measurement
limitation of this harness under its own worst-case fire rate, not a
platform dispatch number**, and should not be quoted as one. The
republish leg's figures, measured on a leg with no fast bucket to
saturate the stream, are the reading closer to what a normal subscriber
would see: comfortably inside the per-fire budget.

## Verdict

**The two halves of the pre-registered budget turn out to be one
violation, not two.** `BURST` and `ONESHOT_ANCHORED` fires never
exceeded ~300ms of drift anywhere in this run (87,997 reducer calls, idle
and under 10,000-row load alike) -- the per-fire budget genuinely holds
for any shape that does not reschedule from its own actual fire time.
But for `ScheduleAt::Interval` and the hand-rolled chained one-shot, a
"single fire's" drift *is* the cumulative slip up to that tick, because
each one reschedules from where the last one landed -- so the per-fire
budget is not merely at risk for these shapes, it is directly violated by
them: `idle-interval-100`'s last recorded fire landed **159.9 seconds**
late, `idle-oneshot-100`'s **159.9 seconds** late, both far past the
2.5s budget, and both would have crossed it by roughly tick 263 (~26s of
wall-clock time at a 100ms bucket, ~4 minutes at a 1s bucket). The
non-compounding requirement is not a separate, softer concern from the
per-fire budget for these two shapes -- it is the mechanism by which they
eventually break it.

**The rate, and what holds instead.** Both compounding shapes grow at
+7.4 to +11.2 ms/tick, at every bucket from 100ms to 600s, idle and under
load alike -- over a session-length run this walks a naive
interval-driven day-night cycle or L2 tick arbitrarily far from real
time, the failure mode risk **R10** names. A one-shot chain that
reschedules from its own fixed-origin target instead of from `fired_at`
held phase for the entire 31-minute run with no accumulation (-0.32 to
+2.94 ms/tick, no trend) at every bucket tested. Whether the compounding
behaviour is `ScheduleAt::Interval` reflecting undocumented-but-intentional
semantics or a defect is not something this run can answer:
SpacetimeDB's own schedule-tables documentation does not state which
reference point a repeating schedule reschedules against, so the appeal
to a closed upstream GitHub issue this report's cycle 1 draft made is
dropped here rather than repeated on a citation nobody confirmed
describes this exact behaviour.

**Per this report's pre-registered rule: decision D7 (the Alarm Clock)
is reopened**, because the platform's own repeating primitive, used the
way a first implementation would reach for it, compounds without bound.
This PR does not resolve D7 by prescribing the schedule-time-anchored
pattern as the fix -- that is a design decision for whoever revisits D7,
not a correction folded into this spike -- but it hands that decision a
measured candidate rather than an unmeasured one: a repeat that
reschedules from its own intended time, not from when it last actually
ran, held phase indefinitely in this run at every bucket and under load,
for a per-fire jitter cost of single-digit milliseconds. That candidate
is not free of hazard on its own: seeded already behind, it dispatched a
bounded but real back-to-back catch-up burst (~75 fires/second) rather
than gliding back to phase gently, so it converges rather than holding
indefinitely without a pause -- see the Catch-up leg above. `docs/
architecture.md` records the timeless residue: the 2.5s per-fire budget,
that a repeating schedule must be built the phase-preserving way to be
trusted over a session-length run, and that the phase-preserving way must
also bound its own catch-up.
